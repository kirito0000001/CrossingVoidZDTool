# 重构方案

> 前置阅读：`01-现状诊断.md`

---

## 0. 方案定位

**不是「引入架构」，是「把漂移收回来，并且让它不再漂」。**

`Docs/MvvmAndUxGuidelines.md` 已经把目标架构写清楚了，MVVM 的基础设施（`ObservableObject` / `RelayCommand` / `AsyncRelayCommand`）也早就写好了。缺的是三样东西：

1. **纪律的载体** —— 规则只写在文档里，没有任何代码结构或测试去强制它
2. **横切设施** —— 日志、原子写、进程编排、通知传播都没有统一入口，于是每个人各写一套
3. **能验证行为的测试** —— 现有测试大量断言源码文本，反而把反模式锁死了

方案按这三样来组织。

### 三条硬约束

| 约束 | 含义 |
|---|---|
| **单人维护** | 不引入 DI 容器、不引入 mock 框架、不做微服务式过度分层 |
| **增量落地** | 每一步都能单独提交、单独跑 247 个回归测试、随时可停 |
| **不大爆炸** | 任何一步失败都不影响下一步；不存在「改到一半不能用」的中间状态 |

## 3. P1：横切设施

这一阶段不动任何业务逻辑，只是把「每个人各写一套」变成「一处实现」。

### 3.1 `Services/Infrastructure/IToolboxLog`（最重要）

**问题**：Services 层 16800 行、约 90 处 `catch`，**0 处日志出口**。每次静默吞异常都不留痕迹。

```csharp
internal interface IToolboxLog
{
    void Info(string message);
    void Warn(string message, Exception? error = null);
    void Error(string message, Exception? error = null);
}
```

- 默认实现空操作，所以现有 `new XxxService()` 调用点**一行都不用改**
- 组合根注入接到 `MainWindow.Logging.cs` 的 `AppendLog`
- **规则：从此每个 `catch` 要么向上抛，要么写一行日志说明为什么吞。不允许静默 `catch`。**

这一条单独就能显著降低「显示成功但实际没做成」这类问题的排查成本。

### 3.2 `Services/Infrastructure/AtomicFileWriter`

消灭散落 12 个文件的 `.tmp + File.Move` 复制代码和 6 份 `TryDelete`。

```csharp
static void WriteAllText(string path, string text, Encoding? encoding = null);
static void TryDelete(string path);
static bool TryMoveWithRetry(string source, string destination, int attempts = 3);
```

顺手补上**当前完全没有的重试**——Unreal 正在读文件时写入会直接抛 `IOException` 给用户。

### 3.3 `Services/UnrealBridge/UnrealProcessRunner`

消灭 4 份 `KillProcessTree` + 4 份进度轮询（间隔还各不相同：1000/750/500/500ms）。

⚠️ **保留一个已踩过坑的行为**：`UnrealProjectSyncService.cs:735-760` 是「以清单新鲜度而非退出码判成败」（代码注释写明了原因——commandlet 退出码不可靠，任何无关的编辑器错误都会让它非零）。这个判定必须作为可选回调保留，**不能内联进通用逻辑**。

### 3.4 常量外提

- `Services/UnrealBridge/UnrealContentPaths.cs` —— 断掉底层服务对 3186 行 God Class 的反向引用（现有 14 处）
- `Services/Workspace/CharacterFolderLayout.cs` —— 统一跨 5 个文件重复定义的 `"tool"/"AssetMaterial"/"ZDMaterial"/"Sound"/"BUFF"` 等常量

## 5. P3：通知机制换成声明式

### 5.1 建议引入 CommunityToolkit.Mvvm

**关键收益不是 `[ObservableProperty]` 省样板，而是 `[NotifyPropertyChangedFor]` 把「派生属性依赖」从注释变成编译期声明**：

```csharp
[ObservableProperty]
[NotifyPropertyChangedFor(nameof(WorkspaceState))]
[NotifyPropertyChangedFor(nameof(CanAdvanceWorkflow))]
private bool hasImportDetection;
```

这直接消灭「某条路径忘了通知」这一整类 bug —— 也就是本项目已经踩过两次（中栏空白、第 3/5 步勾选计数）、且还有 11 处潜伏的那类。

**适配性**：8.x 是纯源生成器，无运行时依赖，AOT/trim 友好，和 `net8.0-windows` + WinUI 3 兼容。基类 `ObservableObject` 同名且 `SetProperty` 签名兼容，替换面小。

**只用一半**：`Ioc` 和 `Messenger` 不要用，单人工具不需要。

**分两步**：
- **3a**：只在 `UnrealProjectSyncViewModel` 的 46 个字段支撑属性上用，删掉 `WorkflowStep` setter 里那 25 行手工通知
- **3b**：`RelayCommand`/`AsyncRelayCommand` 换成 `[RelayCommand]`。⚠️ 自写的 `AsyncRelayCommand` 有 `allowsConcurrentExecutions` 和 `ExecutionFailed` 两个 Toolkit 没有的特性，**先补测试再换**

### 5.2 把已有的「自监听」模式补全

`UnrealProjectSyncViewModel.Workspace.cs` 的 `AttachWorkspaceWatchers()` 是正确方向，但白名单只认 3 个属性名，而 `WorkspaceState` 实际读了 **11 个输入**——剩下 8 个仍靠手工通知。

两处要改：
- 白名单**反转**为「排除已知无关属性」，或干脆去掉过滤（有值相等守卫兜底，成本可控）
- 相等性守卫的比较键从单个枚举换成 `(WorkspaceState, WorkflowStepName, PlaceholderTitle, PlaceholderDescription)` 元组 —— 否则同一枚举值下的文案变化会被吞掉

### 5.3 清理冗余状态（约 25 个字段）

- 6 个 `_import*CountText` → 派生属性
- 7 个 `_detection*Count` → 直接持有变更列表现算
- `_lastLightConfigurationItems` / `_lastBlueprintSetupItems` 两份平行 List → 删掉，计数从 `ObservableCollection` 算
- `_isNormalizationWorkspace` → 改为 `=> WorkflowStep == 2 && IsPublishDetection`（消 8 个赋值点）

## 6. P4：View ↔ VM 接线改造

> ⚠️ **前置条件：必须先把 73 处源码文本断言换成行为断言**，否则每搬一块都会撞一片红。见 `01-现状诊断.md` §5.5。

### 6.1 三个 View 层抽象（一次性，解开硬耦合）

| 抽象 | 吃掉什么 | 成本 |
|---|---|---|
| `IFilePickerService` | 9 处裸 `FileOpenPicker/FolderPicker` + `InitializeWithWindow` | **极低**（半天） |
| `INotificationService` | `ShowFloatingTip` + `AppendLog`，让 VM 能直接报错 | 低 |
| `Controls/OverlayHost.xaml` | 12 个遮罩层重复的 Esc/右键/点外关闭 + 动画，约 60 个事件处理器 | 中 |

`INotificationService` 其实已有雏形——`IUnrealSyncWorkflowHost` 的 `Notify`/`Log` 两个方法，直接提出来做成全项目共用即可。

### 6.2 P0 级：`MainWindow.UnrealSync.Publish.cs:24-606`

**583 行的单个 `async void` 事件处理器**，在一个按钮回调里做了：进度计划分配、导出、规整校验、快照构建、差异比对、基线迁移、序列发布、执行器调用、Python 任务构建、复扫验证，并在每个 catch 里回退步骤。同文件的注释已经承认了这个坑（「按钮处理器是 async void：流程编排 await 不到它」）。

**改法**：照抄 `UnrealSyncWorkflowController` 的 `Controller + IHost + 领域化 Notice 类型` 模具。

⚠️ **别重复它的一个缺陷**：`RunStepDetectionAsync` 目前是「万能逃生舱」，实现里又调回 6 个留在 MainWindow 的方法。搬 Publish 时不要照抄这一点，否则只是把复杂度挪了个位置。

### 6.3 明确**不做**的三件事

| 不做 | 理由 |
|---|---|
| **拆多个 Page + Frame 导航** | 9 个页面共享一个 `ApplicationViewModel` 和大量交叉状态；12 个遮罩层是跨页的（`Grid.RowSpan="2"`），`Frame` 里放不下；页面动画和滚动位置保持都是围绕 Visibility 模型写的。成本远超收益 |
| **引入 DI 容器** | 手写组合根 85 行已经清楚，容器只增加启动开销和 trimming 风险 |
| **`{Binding}` 全量换 `{x:Bind}`** | 528 处，单根 DataContext 下 `{Binding}` 工作良好。只在**新写**的部分用 `x:Bind` |

**`MainWindow.xaml` 5522 行的替代解法**（成本 1/10，收益 80%）：把 12 个遮罩层各自抽成 `Controls/XxxOverlay.xaml`，MainWindow.xaml 只留一行引用。能把 XAML 从 5522 砍到约 3300 行，**且不动导航模型**。项目里已有先例 `SkillEditorControl.xaml`。

## 7. P5：六步流程状态对象化

这是解决 93 个字段的根本办法，但**不急**，建议放最后。

```csharp
internal sealed record UnrealSyncStepState(
    bool IsLoaded, bool IsRunning, string Failure, int ItemCount, string Summary);

internal sealed class UnrealSyncWorkflowState   // 纯领域对象，不继承 ObservableObject
{
    public int CurrentStep { get; }
    public IReadOnlyDictionary<int, UnrealSyncStepState> Steps { get; }
}
```

收益：把 7 个分散的步骤标志合并成一张按步索引的表；`WorkspaceState` 那 60 行嵌套三元变成一次查询；**可以脱离 WinUI 单测**；`UnrealSyncWorkflowController` 不再需要依赖 2733 行的具体 VM 类型。

**落地顺序**：先做只读投影（VM 内部 `BuildState()`，让 `WorkspaceState` 走它），验证 21 个现有用例全绿，再逐步把字段迁进去。

## 8. 防止再次漂移的机制

这是整个方案里**最重要**的一节——没有它，上面所有工作会在几个月后回到原点。

| 机制 | 做法 |
|---|---|
| **测试断言行为，不断言源码** | 把 73 处文本断言逐步换成行为断言。新增用例一律不许 `File.ReadAllText` 源码 |
| **文件体量护栏** | 加一个回归用例：任何 `MainWindow.*.cs` 超过 N 行就失败。N 取当前最大值，只允许降不允许升 |
| **禁止静默 catch** | P1 的 `IToolboxLog` 落地后，加一个用例扫描 Services 层的空 `catch` 块 |
| **分类表漂移校验** | 语音分类当前有 4 份手工维护的表且**一条校验都没有**（序列动作表有）。补齐 |
| **新代码规则** | 新按钮一律 `Command={Binding}`；新 `DataTemplate` 用 `x:Bind` + `x:DataType`；不回头改存量 |

护栏用例的写法可以参考现有的 `SequenceActionCatalogMatchesExporterSpecs`——它已经在防 C#↔Python 的动作表漂移了，是现成的模具。
