# 现状诊断

> 调查时间：2026-09-08　分支：`feat/refactor`（起点 `27a55d6`）
> 方法：5 个并行子分析 + 逐条人工复核。**本文档中的每条结论都经过实测复核**，未复核的推断单独标注。

## 0. 一句话结论

**问题不是「没有架构」，而是「有架构、但没有任何机制拦住代码偏离它」。**

`Docs/MvvmAndUxGuidelines.md`（367 行）早就写明了分层、MVVM 规则、命令链路，甚至结尾专门警告：

> 最后提醒：别把项目养成一个超大的 `MainWindow.xaml.cs`。业务逻辑往 Service 走，页面状态往 ViewModel 走。

而实际代码：

| 规约怎么写的 | 代码实际怎样 |
|---|---|
| `XAML/Button → ViewModel Command → Service → Result → ViewModel State → Binding` | `Command=` 出现 **0** 次，`Click=` **132** 次，事件处理器 **257** 个 |
| 异步命令用 `AsyncRelayCommand` | `AsyncRelayCommand` 132 行，实例化 **0** 次（死代码） |
| MainWindow 只做外壳桥接 | MainWindow 分部 **11248 行**，含 583 行的单个 `async void` 业务编排 |
| ViewModel 暴露状态不暴露控件 | `UnrealProjectSyncViewModel.Workspace.cs` 直接暴露 `Visibility` 类型 |
| 业务逻辑往 Service 走 | Services 层 16800 行，但**整层 0 处日志出口**，约 90 处 `catch` 全静默 |

更关键的是：**回归测试把反模式固化成了断言**（详见 §5），任何朝规约靠拢的改动都会先撞上一片红。这是漂移能持续的直接原因。

## 4. ViewModels 层（22 文件 / 8656 行）

### 4.1 做得好的部分

- **VM 之间耦合极低**：唯一的 VM→VM 引用是 `UnrealSyncWorkflowController → UnrealProjectSyncViewModel`
- **零全局可变状态**：30 个 `static` 成员全是纯函数或不可变常量表
- **VM 里没有文件 IO / 起进程 / 解析 JSON**（比预期好）
- **没有跨线程改集合**；`ConfigureAwait(false)` 只用在 3 处会话缓存落盘且注释说明了防死锁意图

### 4.2 核心问题：通知全靠手工，没有任何机制

`ObservableObject.cs` 只有 `SetProperty` + `OnPropertyChanged`，**没有依赖声明、没有自动传播**。`UnrealProjectSyncViewModel` 有 **90 个派生属性**、**185 处手工 `OnPropertyChanged`**，构成一张纯手工维护的依赖网。

最极端的是 `WorkflowStep` 的 setter 一次列了 **25 条**通知，其中 `WorkflowNextButtonEnabled` 被重复写了两遍，还有两行缩进错位——手工维护的疲劳痕迹清晰可见。

**已确认 11 类漏通知实例，详见 `03-缺陷清单.md`。**

### 4.3 冗余状态（约可删 25 个字段）

- 6 个 `int` 计数 + 6 个对应的 `string` 文案字段（后者是纯格式化，应改派生属性）
- `_lastLightConfigurationItems` / `_lastBlueprintSetupItems` 是 `ObservableCollection` 的平行 `List` 副本，两边必须手工保持一致
- `_isNormalizationWorkspace` 与 `WorkflowStep == 2` 语义重叠，有 8 个赋值点，其中一处写的正是 `cache.IsPublishDetection && WorkflowStep == 2`——自证冗余
- 7 个 `_detection*Count` 只服务于一个字符串

### 4.4 `UnrealSyncWorkflowController` — 最好的范本

238 行，做对了三件事：用 `IUnrealSyncWorkflowHost`（3 个方法）切断 UI 依赖；提炼了 UI 无关的领域类型（`UnrealSyncNotice`/`UnrealSyncStepGate` 而非 `InfoBarSeverity`）；把判定与副作用分离（`CanLeaveStep` 是纯查询）。测试侧 `FakeWorkflowHost` 能真跑六步。

**仍未解决**：只搬走了编排没搬走状态，仍直读 VM 的 6 个属性且依赖 2733 行的具体类型；`CanLeaveStep` 与 VM 的 `CanAdvanceWorkflow` 语义重叠、规则分裂在两处；`RunStepDetectionAsync` 是个「万能逃生舱」，实现里又调回 6 个留在 MainWindow 的方法。

## 5. UI 层：MVVM 的真实状况

### 5.1 不是「没有 MVVM」，是「View 不用绑定去消费 VM」

| 指标 | 实测 |
|---|---:|
| `{Binding}` | **528** |
| `{x:Bind}` | **0** |
| `Command="{...}"` | **0** |
| `Click="..."` | **132** |
| XAML 事件属性总数 | **257** |
| 对应的 code-behind 事件处理器 | **257** |
| `AsyncRelayCommand` 实例化 | **0** |
| `RelayCommand` 实例化 | 1（且未走 `Command=` 绑定，是键盘快捷键触发） |

ViewModel 层写了 8656 行且质量不低，绑定路径分布（`UnrealProjectSync` 93 条、`SequenceFrames` 51 条…）说明 VM **确实在被消费**。债在「View↔VM 的接线方式」和「几个巨型事件处理器里的业务编排」。

### 5.2 页面切换：没有 Frame，9 个页面同时驻留内存

`NavigationView` → `Tag` 字符串 → 手写 `if/else` 分派 → `ShowOnlyPage()` 逐个设 `Visibility`。**9 个页面的可视树永远同时存在**，这是 XAML 单文件 5522 行的根因。

另有 **12 个手写的全屏遮罩层**（不是 `ContentDialog`，是 `Grid.RowSpan="2"` + 自己接 `Tapped`/`KeyDown`/`RightTapped` 三件套），约 60 个事件处理器纯粹是这套模板的重复。

### 5.3 已经抽象好的（好消息）

`Services/WinUiDialogService.cs` + `DialogContracts.cs` 已把 `new ContentDialog` 封在一处，14 个调用点全部走服务，统一处理了 Esc/右键关闭和 `CancellationToken`。

**但抽象是漏的**：`ContentDialogRequest.Content` 类型是 `UIElement`，调用方仍必须构造 UI，ViewModel 无法直接调用——这是 MVVM 迁移的第一道真实阻力。

### 5.4 完全没抽象的：9 处文件选择器

每处都跟着 `InitializeWithWindow.Initialize(picker, WindowNative.GetWindowHandle(this))`——**`this` 必须是 `Window`**，这是把这些方法钉死在 `MainWindow` 上的硬约束。

### 5.5 ⚠️ 测试把反模式固化成了断言

**✅ 已复核**：测试里有 **73 处**对 MainWindow 源码做文本断言，其中锁死 `MainWindow.xaml` 的有 **38 处**。样本：

```csharp
xaml.Contains("x:Name=\"VoiceMaterialAssignmentBar\"")              // 断言具名元素存在
xaml.Contains("Text=\"当前帧语音\"")                                 // 断言界面字面文案
xaml.Contains("Click=\"ResolveAllSequenceFrameDuplicatesButton_Click\"")  // 断言事件接线方式
formLimitIndex >= 0 && antiIndex > formLimitIndex                   // 断言元素在文件里的先后顺序
```

最后那条 `Click=` 断言**直接钉死了「必须用事件处理器、不能改 Command 绑定」**。把遮罩层抽成 UserControl 会让这批断言集体失败——不是因为功能坏了，而是因为字符串搬了家。

**这决定了迁移顺序：必须先把文本断言换成真断言，再搬代码。** 反过来做的话每搬一块都要面对一片红，人会很快放弃。项目里已有正确做法的先例：`UnrealSyncWorkflowController` 配 `FakeWorkflowHost`。
