## 一、结论先说

**做成「进程 + 文件」两段式，不做 C# 重写、不 Embed Python。**
**两套实现（Python + Node）全部搬进工具箱，`D:\图集\` 之后删掉 —— 一个程序不拆两半。**

工具箱只负责三件事：

1. **把清单写出去**（它已经有这个数据了，就是 `sequence.json`）
2. **起一个进程**（复用 `UnrealProcessRunner`）
3. **把产出的尺寸读回来**（`--report`）

工具箱**永远不知道**装箱、旋转、密度这些概念 —— 那是图集工具内部的事。
这条边界划清楚，两边就能各自演进。

---

## 二、为什么不是另外两条路

| 方案 | 否决理由 |
|---|---|
| **C# 重写装箱** | 等于长期维护两份实现。图集工具那 55+33 项自检、拆 TexturePacker DLL 得来的算法结论、旋转取图约定，全部要重新踩一遍。而且它那个 `grid` 模式（给 Niagara SubUV）是独有的，重写还得再实现一遍。 |
| **Embed Python（Python.NET）** | 把「进程边界」换成「运行时边界」，耦合更紧不是更松：Python 版本、Pillow 依赖、异常跨语言传递，全都变成工具箱的启动负担。而且失败时会**拖垮主进程**，而进程方式最多是子进程挂掉。 |
| **进程 + 文件（采纳）** | 已有 `UnrealProcessRunner` 解决退出码不可靠 / 杀进程树 / 进度轮询；已有 `AtomicFileWriter`；Python 侧自检不需要 Unreal 就能跑（和现有 `check_export_asset_paths.py` 一个套路）。 |

## 四、接口契约（工具箱 ↔ 图集工具）

### 4.1 出去：清单文件

图集清单的来源是**素材目录**（`ZDMaterial/<动作>/Frames/`），**不是序列清单**。
这一条在 2026-09-15 更正过，理由见 §4.2。

| 图集清单字段 | 来源 |
|---|---|
| `frames[].file` | 素材目录里的 PNG 绝对路径（扫目录得到） |
| `frames[].name` | 与 Unreal 侧**同一套命名函数**生成（见 §4.3） |
| `frames[].index` | **该图在扫目录结果里的下标 +1**（1 起） |
| `atlas` | `<角色代号>_<动作代号>` |

扫描规则：**只认 `.png`、不递归子目录、按文件名升序**。
顺序对图集无意义（决定播放顺序的是同步阶段的 Flipbook 索引），只要有**稳定**顺序即可。

### 4.2 `frames[]` 以**素材库**为准，不跟随序列清单

> ⚠ **这一节在 2026-09-15 被推翻重写过。** 旧版本写的是「复用帧每个位置各出一条」，
> 那是**错的** —— 它把「素材」和「序列」两件事混成了一件，导致 Sk2 的图集
> 打出 23 个格子，而素材目录里其实只有 17 张 PNG：**6 张图白占地方**。

先说清两件事的区别：

| | 回答什么问题 | 谁负责 |
|---|---|---|
| **序列清单** `sequence.json` | 「这条动画第几格放哪张图」——同一条路径可以**被引用多次**（复用） | 序列编排（St5 / 同步序列） |
| **素材目录** `Frames/` | 「素材库里到底有**哪几张图**」 | 素材管理（St5 导入） |

**图集只管后者。** 规则一句话：**目录里有几张 PNG，就打几个格子。**

#### 为什么旧做法是错的

旧做法从序列清单推导帧列表，于是把复用位置各出了一条。Sk2 的实际数据：

```
素材目录 Frames/        ->  17 张 PNG
sequence.json          ->  23 条（位置 6~11 与 18~23 复用同一批图）
旧的图集产物            ->  23 个格子  ❌  6 张图白占地方
现在的图集产物          ->  17 个格子  ✅
```

两个具体危害：

1. **文件占用翻倍**（晓桀的核心诉求是「以最少的文件占用来制作」）。
2. **把判断权交给了代码**。按清单推算要「猜」哪个是复用、要不要合并，
   一旦清单漏引用了某张图（素材在，但序列里没用上），图集就会**漏打这张图**。
   按目录扫则是**零判断** —— 不猜，也就没有判断失误的余地。

#### 那 Flipbook 少了 6 帧怎么办？

**不管。** Flipbook 的索引是**同步序列**那一步的事：

- 一个素材 = 一个 sprite（这是晓桀定的）
- Flipbook 里排好顺序即可，23 格可以重复指向同一个 sprite
- 跨序列引用（同一张图被 Sk2 和 Sk3 同时用）也在这层解决

> 晓桀原话：「**图集其实就管好图集的事情，flipbook 和图里面的索引应该是属于同步序列步骤那边管理的。
> 这点是我疏忽了，不应该现在考虑的。**」
>
> 若 Flipbook 因此出问题，「那就出问题吧，这个之后要用 ZDBridge 去修」—— 不在图集这一步处理。

#### 这里保留的实机事实（仍然有效，只是结论不再从这里推）

下面这些是查证过的**事实**，但它们说明的是「Unreal 侧现在是什么样」，
**不是**「图集该打成什么样」：

**Flipbook 侧代码（`Tools/UnrealBridge/sync_character_sequences.py:559-592`）**

```python
for ordinal, frame in enumerate(frames):
    if frame.get('isBlank'):
        imported.append(None)          # 空白帧不建贴图，但占数组一位
    ...
sprites = [None] * len(frames)          # 按帧数预分配
frame_runs = [max(1, int(frame.get('durationFrames', 1) or 1)) for frame in frames]
```

**C++ 侧（`ZDBridge/Source/ZDBridge/Private/ZDBridgeLibrary.cpp:97-102`）**

```cpp
for (int32 Index = 0; Index < Sprites.Num(); ++Index)
{
    FPaperFlipbookKeyFrame& Key = KeyFrames.AddDefaulted_GetRef();
    Key.Sprite   = Sprites[Index];
    Key.FrameRun = FrameRuns.IsValidIndex(Index) ? FMath::Max(1, FrameRuns[Index]) : 1;
}
```

→ **`key_frames` 的数量 == 序列帧清单的长度**，`FrameRun`（驻留格数）**完全不改列表长度**。

#### 实机验证（`C:\CrossingVoid`，Misaka，2026-09-15）

| 动作 | 素材目录 PNG | 序列清单条目 | UE sprite 数 |
|---|---|---|---|
| Click | 4 | 4 | 4 |
| Death | 8 | 8 | 8 |
| Defeat | 1 | 1 | 1 |
| Flying / FlyDown / FlyStart | 1 | 1 | 1 |
| **Sk2** | **17** | **23** | **23** |
| Ko | — | 31 | 31 |
| Victory | — | 19 | 19 |

**Sk2 这一行是关键**：素材 17 张，Unreal 里却有 23 个 sprite ——
说明**导出那一步把复用位置也各建了一份资产**（23 个 texture + 23 个 sprite）。

> 🔴 **这是导出侧（`export_zd_assets.py`）的问题**，不归图集管，要单独修。
> 图集的职责只是：素材目录里有 17 张，就打 17 个格子。

**复用帧的实机证据**（读 `.uasset` 里的源贴图名）：

```
KO_Frame00.uasset        -> Misaka-Victory-404eff5af365cdcf.png
Victory_Frame00.uasset   -> Misaka-Victory-404eff5af365cdcf.png   ← 同一个源文件
Sk2_Frame05.uasset       -> Misaka-Sk2-5ae23a0f49d9f90e.png
Sk2_Frame17.uasset       -> Misaka-Sk2-5ae23a0f49d9f90e.png       ← 同一个源文件
```

#### 修正后的硬规则

1. **`frames[]` 的条数 = 素材目录里的 PNG 张数**（不是序列条目数）。
2. **同一张源图只出**一条**记录** —— 一个素材对应一个 sprite。
   序列里引用了几次，那是序列的事。
3. **空白帧的概念从图集侧消失**。目录里没有对应文件就是没有，
   不需要 `IsBlank` 判断（素材池那边仍保留这个概念，图集不关心）。
   而**序号绝不能因为跳过它而压缩** —— 序号是资产名的组成部分（见 §4.3）。


### 4.3 精灵名必须复用 Unreal 侧同一套生成规则

**这是全套方案里最容易出错的一处。** 图集工具产出的 `_sequence.json` 是给
Unreal 侧建 Flipbook 用的，`name` 字段就是将来的 **Sprite 资产名**。
它必须和 `SequenceActionCatalog` 算出来的一模一样，否则同步时会认为「这是个新增 sprite」，
插进去一份重复的。

现成函数（**直接调，不要重写**）：

```csharp
SequenceActionCatalog.GetFrameTextureName(definition, formIndex, ordinal, totalFrameCount)
// => "<VariantCode>_Frame<补零序号>"    例：Misaka_Sk2_Frame00
SequenceActionCatalog.GetFrameSpriteName(definition, formIndex, ordinal, totalFrameCount)
// => 上面那个 + "_Sprite"               例：Misaka_Sk2_Frame00_Sprite
```

规则细节：**序号从 0 开始**，位宽 = `MaterialSequenceNaming.GetWidth(totalFrameCount)`
即 `totalFrameCount.ToString().Length`（十张就是两位 `00..16`）。

> 📌 **`totalFrameCount` 现在是「素材张数」**，不是序列长度。
> 例：Sk2 有 17 张素材 → `Sk2_Frame00_Sprite` … `Sk2_Frame16_Sprite`（两位）。
>
> 这与 Unreal 侧现有的资产名**会不一致**：实机 Sk2 是 23 个 sprite
> （`Sk2_Frame00` ~ `Sk2_Frame22`），因为导出那一步把复用也各建了一份。
> 那是导出侧待修的问题（见 §4.2）。图集先按「素材张数」出，名字规则复用同一个函数，
> 等导出侧修好、两边都变成「一个素材一个 sprite」时自然对齐。
>
> ⚠️ `ordinal` 与「空白帧占位」的关系**在图集侧已不适用**（图集不再有空白帧概念）。
> 素材池侧仍保留该规则（`UnrealBridgeSequencePublishService.cs:189-206`）。

### 4.4 回来：`--report` 的结果

按你的要求「**只给尺寸就行了**」：

```json
{
  "ok": true,
  "atlas": "Misaka_Sk2",
  "size": { "w": 1114, "h": 1018 },
  "image": "Misaka_Sk2.png",
  "frameCount": 17
}
```

（上面是 **2026-09-15 用真实 Sk2 素材跑出来的实值**：17 张 PNG → 1114×1018，密度 94.3%。）

工具箱只需要 `size.w` / `size.h`（显示 + 记进清单）。其余字段留着不解析也没关系。

> ⚠️ `frameCount` 是**图集里的格子数**，等于素材张数（不是序列条目数）。
> 若以后同步阶段要拿它去对齐 Flipbook 的 23 格，**对不上是正常的**，
> 那时候要用的是「素材 → 位置」的映射，不是这个数字。

> 📌 **前提**：`--report` 是**唯一的返回值**。退出码不可靠这条在 Unreal 侧已经吃过亏
> （`CONTEXT.md` 里写着），Python 侧同理。判定成败一律**看 report 文件是否新鲜且 `ok:true`**，
> 不看退出码。

### 5.4 Python：**内置一个**（已拍板，且已实测跑通）

晓桀原话：「**内置一个吧，也不大。**」—— 实测下来确实不大，见下面的数字。

#### 实测体积（2026-09-15 真下的包，不是估的）

| | 体积 |
|---|---|
| `python-3.13.14-embed-amd64.zip`（下载包） | 10.5 MB |
| 解压后 | 21 MB |
| **加 Pillow 11.3.0 后（实际要进仓库的）** | **35.2 MB** |
| **压缩后（git 里增加的量）** | **17.7 MB** |

> 参照：本机完整版 Python 是 **165MB**（其中 `Doc/` 62MB、`tcl/` 7MB 都白搭），
> embeddable 省掉的就是这些。**17.7MB 进 git 完全可接受**，「也不大」这个判断是对的。

#### ⚠️ 实测踩到的坑：`_pth` 必须显式加一行，否则 PIL 导不进来

embeddable 包靠 `python313._pth` 做**路径隔离**（不读注册表、不读环境变量），
它默认只有两行：

```
python313.zip
.
```

**这种状态下 `import PIL` 直接 `ModuleNotFoundError`** —— 我把 `PIL/` 放进
`Lib/site-packages/` 之后仍然找不到，因为 `_pth` 模式**不会自动加 site-packages**。

修法是把 `_pth` 改成三行：

```
python313.zip
.
Lib/site-packages
```

改完 `import PIL` → `11.3.0`，实测通过。
**这一条一定要写死进部署步骤**，否则「解压完看起来对、一跑就找不到模块」。

#### 为什么 Pillow 要「解进去」而不是 `pip install`

embeddable 包**不含 pip**（无 `ensurepip`，也不认注册表）。
常见做法是「解压 → `get-pip.py` → pip install」，但那需要**联网**，
还会在用户机器上留 `Scripts/` 和一堆中间产物。

**改用「解压即用」**：Pillow 的 wheel 里就是一个顶层 `PIL/` 目录，
直接整目录拷到 `Lib/site-packages/PIL/` 即可。**不联网、不调 pip、不留中间文件。**

Pillow 的 C 扩展（`_imaging.cp313-win_amd64.pyd` 等 8 个 `.pyd`）就在 `PIL/` 目录里，
embeddable 的 loader 能直接吃 —— **实测通过**，见下。
