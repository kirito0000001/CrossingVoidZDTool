# 语音分类专项

> 对应你提出的两个已知问题：
> 1. 音分类多加一个「音效」分类
> 2. 失败语音也被同步到了虚幻的 `Other`
>
> 本文档中标 ✅ 的结论均已实测复核。

---

## 1. 现状：分类的事实来源在哪

### 1.1 唯一权威定义

| 位置 | 内容 |
|---|---|
| `Models/VoiceMaterialModels.cs:9-23` | `enum VoiceMaterialKind`：Formation, Click, Hurt, Death, Defeat, Victory, Skill1, Skill2, Ultimate, Support, Combo, Other（12 个） |
| `Services/VoiceMaterialService.cs:18-32` | `Specs` 数组 `(Kind, DisplayName, FolderName, FileSuffix, IsRequired)` —— **单一事实来源**，UI、目录名、文件后缀、必填性全从这里取 |

`FolderName` 同时是工具箱本地目录名和 Unreal 目录名。**Python 侧完全不参与目录决策**——`execute_unreal_bridge.py` 只照抄计划里的 `TargetObjectPath`。

### 1.2 但实际上有 4 份手工维护的分类表，互不校验

| # | 表 | 位置 | 用途 |
|---|---|---|---|
| 1 | `Specs` | `VoiceMaterialService.cs:18-32` | 权威 |

| 3 | 动作码 → 分类 switch | `UnrealBridgeVoiceClassification.cs:49-61` | 从序列动作反推分类 |
| 4 | 动作码 → 分类（**另一份**） | `ViewModels/SequenceFramesViewModel.cs:20-32` | 序列帧编辑器的语音下拉过滤 |
| 5 | 中文标签 dict（Python） | `Tools/UnrealBridge/configure_unreal_light_settings.py:40-53` | 第四步界面显示 |

**第 5 项已经漂了**：

```
Python  "Formation": "入队语音"    ←→   C#  "编队语音"

```

序列动作表有漂移校验测试（`SequenceActionCatalogMatchesExporterSpecs`），**语音分类一条都没有**。

## 2. 问题 2：失败语音落到 `Other`

### 2.1 ✅ 根因（已复核）

**发布方向本身没有能力「发明」`Other`** —— `ResolveAddedTargetObjectPath` 严格按工具箱 payload 里的 `kind` 取 `FolderName`。所以 `Sound/Other` 里出现失败语音，说明**这条语音在工具箱侧就已经在「待分配」桶里**，误分类发生在**从 Unreal 导入时**。

罪魁在 `Services/UnrealProjectSyncService.cs:2948-2950`：

```csharp
Kind: sequenceKinds.TryGetValue(NormalizeObjectPath(asset.ObjectPath), out var sequenceKind)
    ? sequenceKind                                    // ← 命中就用，是 Other 也用
    : UnrealBridgeVoiceClassification.Classify(...)   // ← 只有没命中才看名字
```

**序列反推的结果只要命中就直接采用，哪怕是 `Other`，绝不回退到按名字识别。**

而 `ClassifySequenceAction`（`UnrealBridgeVoiceClassification.cs:49-61`）只认 **9 个**动作码：

```
click / death / dead / defeat / ondm / ondamage / victory / sk1 / sk2 / ko / sub
```

标准动作表（`SequenceActionCatalog.cs`）有 **19 个**动作。也就是说 **DefAtk、Defence、Dodge、FlyDown、Flying、FlyStart、Idle、Land、Move、StandUp 这 10 个动作全部返回 `Other`**。

> **一条失败语音只要被上述任何一个序列的 PlaySound 通知引用过，就被钉死成待分配——文件名里明写着 `Defeat` 也没用。** 发布时再忠实地把它写回 `Sound/Other`。

`Services/UnrealBridgeDraftImportService.cs:384` 是同一份逻辑的复制品，缺陷一致。

**更致命的路径**：`Tools/Unreal/export_zd_assets.py:1576-1583` 对任何命名不合规范的序列返回 `"actionCode": "Other-" + base_name`。所以只要角色的失败动画被命名成 `XXX_Lose`、`XXX_Defeated_2` 或中文名，挂在它上面的语音必然进 `Other`。

### 2.2 ✅ 次因：Defeat 的 token 覆盖不全（已复核）

`UnrealBridgeVoiceClassification.cs:20`：

```csharp
(VoiceMaterialKind.Defeat, ["defeat", "lose", "failure"]),
```

- ✅ 能识别：`Vo_Defeat1`、`Vo_Defeated1`、`Vo_Lose1`
- ❌ **识别不出**：`Vo_Fail1` —— token 是 `failure` 不是 `fail`
- ❌ 识别不出：`Vo_Lost1`、`Vo_GameOver1`

对比 Hurt 那一行特意加了 `odnm` 这种手工纠错别名，说明作者是照着工程里实际看到的名字一个个补的，Defeat 显然没补全。

### 2.3 ✅ 潜伏隐患：子串匹配整条包路径（已复核）

`UnrealBridgeVoiceClassification.cs:26` 把**整条包路径 + 资产名**拼成搜索串，去掉 `_`/`-` 后做 `Contains`：

```csharp
var searchable = $"/{packagePath}/{assetName}/".Replace("_","").Replace("-","").ToLowerInvariant();
```

于是 2 字符 token 会被角色代号污染，且 **`ko`(优先级 3)、`sub`(4)、`link`(5)、`team`(6) 都排在 `defeat`(10) 前面**：

| 角色代号含 | 后果 |
|---|---|
| `ko`（Kokona、Konno、Nakoruru） | 该角色**全部**语音判为终结技 |
| `sub`（Subaru） | 全部判为护援技 |
| `lose` 也会被 `close` / `loser` 误命中 | |

> 当前工作区的 3 个角色（Misaka、ALO_Yuki、SAO_kirito）**不触发**这条——已逐个验算。属于潜伏风险，不是你当前症状的成因。

### 2.4 ✅ 附带发现：受伤动作的语音下拉完全不过滤（已复核）

`ViewModels/SequenceFramesViewModel.cs:25` 写的是 `("Ondm", VoiceMaterialKind.Hurt)`，但工具箱侧真实动作码是 **`OnDamage`**（`SequenceFrameService.cs:56`）。

匹配函数 `IsActionCodeInFamily` 只接受「完全相等」或「基码 + 纯数字」，而 `"OnDamage".StartsWith("Ondm")` 为 **false**（第 4 个字符 `a` vs `m`）。

后果：`hasMappedKind` 为 false → 过滤条件 `!hasMappedKind || ...` 短路 → **受伤动作的语音下拉列出全部 12 类语音，不做任何过滤**。

现有用例 `SequenceFrameVoicesFilterByActionCategory` 只测了 `Click` 和 `DefAtk`，没覆盖到。

### 2.5 修复建议（按性价比排序）

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| 1 | 序列反推得 `Other` 时**回退到名字识别** | `UnrealProjectSyncService.cs:2948`、`UnrealBridgeDraftImportService.cs:384` | 最可能的根因，改动最小 |
| 2 | 给 Defeat 补 `fail`、`lost` 等 token | `UnrealBridgeVoiceClassification.cs:20` | |
| 3 | `ko`/`sub`/`link`/`team` 改成带分隔符的边界匹配 | 同上 `:26` | 消除代号污染 |
| 4 | 动作码 switch 改走 `SequenceActionCatalog` | `UnrealBridgeVoiceClassification.cs:49` | 消灭第 3、4 号重复表 |
| 5 | `"Ondm"` → `"OnDamage"` | `SequenceFramesViewModel.cs:25` | 或同样改走 catalog |
| 6 | 补 C#↔Python 语音分类漂移校验用例 | 测试 | 照抄 `SequenceActionCatalogMatchesExporterSpecs` |

### 3.3 ✅ 硬编码情况（已复核，结论是好消息）

- **没有** `Enum.GetValues<VoiceMaterialKind>()`、**没有** `(int)` 强转、**没有** `Specs[index]` 下标访问
- **枚举值从不以整数持久化**：payload 一律写字符串（`Kind.ToString()`），读取端用 `Enum.TryParse`
- `AppJsonSerializerContext` 完全不涉及语音类型

**但有 3 处按枚举序数排序**，插在中间会改变行为：

| 位置 | 影响 |
|---|---|
| `UnrealLightConfigurationService.cs:38` | 写进 Unreal 的 `TalkSoundObjectPaths` **数组顺序** |
| `UnrealProjectSyncService.cs:2953` | 语音分组的显示顺序 |
| `UnrealBridgeDraftImportService.cs:400` | 导入顺序，进而影响分配到的**文件编号** |

→ **结论：新枚举成员追加在末尾（或紧邻 `Other` 之前）最安全。**

### 3.4 无需改动

XAML 全部数据驱动（绑 `RequiredVoiceSections` / `OptionalVoiceSections`，单一 `DataTemplate` 复用）；分配菜单从 `Specs` 生成；`export_zd_assets.py`、`execute_unreal_bridge.py`、所有会话缓存/状态模型均不感知语音分类。

### 未证实、需要运行时验证

`UnrealBridgeDiffService` 的规范路径用**未清洗**的工具箱文件名拼，而 Unreal 侧资产名是清洗过的，主匹配必然失败，靠 `NormalizeAssetName`（只保留字母数字）兜底，且**要求兜底候选恰好唯一**。

风险：`Misaka-编队 (1).wav` 与 `Misaka-编队-1.wav` 都规范化成 `misaka编队1` → 候选 2 个 → 配对失败 → 一边判「新增」、一边判「待删除」。另外该函数不做全角折叠，全角数字 `１` 与半角 `1` 不相等。

**验证方法**：造一个同时含 `X-编队 (1).wav` 和 `X-编队-1.wav`（或含全角数字）的角色，跑第三步检测，看是否出现「新增 + 待删除」的重复项。
