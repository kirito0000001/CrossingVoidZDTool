# 序列同步改为图集导入 · 进度与交接

> 写于 2026-09-15。第五步「序列同步」从「逐帧导入 PNG」改成「导入一张图集 + 按矩形切精灵」。
> 这份文档是给下一个接手的人（或上下文压缩之后的自己）看的，只记**事实和证据**，不写推测当结论。

---

## 一、这次要解决什么

原来的链路是：每张 PNG 各导入成一个 Texture，再各建一个 Sprite，最后用这些 Sprite 建 Flipbook。
复用位置会被各导一份，于是 Sk2 素材目录里 17 张图，导入后变成 23 张贴图加 23 个精灵。

改成：一张图集贴图 + 每个素材一个 Sprite，复用位置在 Flipbook 的关键帧层面共享同一个 Sprite。

顺带明确了排序权威：**帧序由工具箱的 `sequence.json` 决定**（含复用与空白帧），
图集的 `<图集名>_sequence.json` 只回答「每张素材在图集里的矩形」，不决定顺序。

## 二、已完成

### 交付层（C#）

| 加了什么 | 位置 |
|---|---|
| 图集帧表的模型（`AtlasSequenceManifest` / `AtlasSequenceFrame` / `AtlasRect`） | `Models/AtlasModels.cs` |
| 帧表读取 + 「必须是本轮产物」的新鲜度校验 + 按序号索引 | `Services/Atlas/AtlasSequenceManifestReader.cs` |
| 同步前给勾选动作打图集（只打勾选的、落 `tool/AtlasCache`、尺寸上限按帧数动态算） | `Services/Atlas/SequenceAtlasPackService.cs` |
| `--max-size` 参数 | `Services/Atlas/AtlasPackService.cs` |
| 计划契约：动作级带 `Atlas` 与 `SourceImages`，帧级带 `SourceImageIndex` | `Services/UnrealBridgeSequencePublishService.cs` |
| 同步流程接线：打包完成后再生成计划（进度条阶段 2/5） | `MainWindow.UnrealSync.Publish.cs` |

尺寸上限按「帧数 × 帧规格(928×640)」的面积开方、向上取到 2 的幂，2048 起、8192 封顶；
它只约束搜索范围，实际用多大由打包器挑、从 report 回读。

### 执行层（Python）

`Tools/UnrealBridge/sync_character_sequences.py`：

- 图集只 import 一次
- `_apply_atlas_sprite` 按矩形建或就地更新精灵，同时写入 `source_uv`、`source_dimension`、
  `b_trimmed_in_source_image`、`origin_in_source_image_before_trimming`、
  `source_image_dimension_before_trimming`、`b_rotated_in_source_image`
- Flipbook 按帧序引用这一批精灵（复用位置共用同一个指针）
- 清理基准改成「图集贴图 + 去重后的精灵 + Flipbook + 序列」

**没有改 ZDBridge 的 C++**。引擎的 `UPaperSprite` 那几个字段都是 `EditAnywhere`，
且 `PostEditChangeProperty` 结尾会走 `RefreshBakedData / RebuildCollisionData / RebuildRenderData`，
所以从 Python 写属性和 `.paper2dsprites` 导入器走的是同一条路。**这次不需要重新编译插件。**

### 差异层

- 序列动作不再走三方比较。载荷格式一换代旧基线两侧都对不上，
  三方比较会把全部动作判成冲突；现在直接比两侧当前载荷（`layout` + `slots` + `blanks` + 代号 + 帧率），
  不一致就是「需要重建」。
- 载荷里的 `layout`：图集布局写 `atlas:<图集名>`，仍是逐帧导入时写实际用到的贴图名集合。
- 计数改成资产口径：新增按素材去重并补一条图集贴图；删除以动作占用资产为准，不再按帧位摊开。
- 动作标题行补现状摘要：`工具箱 N 张素材 · M 个帧位 | Unreal 现有 K 个帧位`。
- 序列专属导出不再递归整个角色目录，只扫角色根（非递归）、`AnimSequences`、`Material`、角色 Item。
  之前虽然事后滤掉了 Sound/BUFF，但扫描本身还是把它们整个走了一遍。

- `python -m py_compile` 通过（`export_zd_assets.py`、`sync_character_sequences.py`）

## 三、还没做完

### 1. 「Unreal 现有 0 个帧位」——已修，但过程值得记下来

现象：中栏的动作摘要里「Unreal 现有 N 个帧位」永远是 0。

**我先误判了两次**，记在这里免得重走：

- 先以为是缓存序列化丢了 `UnrealBridgeChange.UnrealItem`。
  直接打开 `%APPDATA%\CrossingVoidZDTool\UnrealSync\session-*-step5.json` 数，
  `"UnrealItem"` 出现 377 次且值是实对象 —— **序列化没问题**。
- 又以为 Unreal 帧没和工具箱帧配上对。探针数据显示
  `frames=288 withUnreal=154`，154 条是 `Unchanged`（配好对的），134 条是待新增 —— **配对也是好的**。

真实原因：**统计取错了数据源**。`FilterCachedPublishChanges` 会把 `Unchanged` 剔掉
（这是设计：缓存恢复出来的是待办清单），而配对成功的帧正是 `Unchanged`。
拿这份列表去数「Unreal 现有多少帧位」，永远是 0。

修法：帧位数改从**动作节点自己的载荷**里读 —— 动作节点是 `Updated`、不会被剔，
载荷里带着两侧各自的 `slots`。素材张数则按去重后的新增条目数。
读取辅助函数在 `SequenceFrameIdentity.TryReadActionPayload`。

**教训**：判断「数据丢没丢」要先去看磁盘上的产物，别从下游现象倒推。
这次两轮误判都是没先打开那个 6.7MB 的缓存文件看一眼。

### 2. 实机同步从没跑过（**最后验，也最关键**）

精灵的裁剪偏移是这次最脆弱的一环：写错不会报错，只会每帧被贴到画布左上角，整条动画抖。
源码语义已核对（`SetTrim` 令 `TopLeftUV = SourceUV - OriginInSourceImage`、尺寸取原图整幅），
但源码对不等于实机对。

建议先拿单个动作跑（Sk2：17 张素材、23 个帧位），在 Unreal 里确认三件事：

1. 贴图只有一张 `Misaka_Sk2`
2. 精灵 17 个
3. 播放时锚点不抖

### 3. 清理临时探针

`ViewModels/UnrealProjectSyncViewModel.cs` 里搜 `[DEBUG-seqfacts]`，定位完删掉。

## 四、几个容易踩的点（记下来免得重走）

- **图集只收 PNG**。素材池允许 jpg/webp/bmp，但图集侧是窄的 —— 混进有损格式会出现
  「本地看着没事、进引擎才发现边缘脏」。计划生成时遇到非 PNG 的帧会当场报错，不会静默当空白。
- **trim 必须开**。928×640 的帧不裁的话，2048 的图集一次只装得下 6 帧，Sk2 那 17 帧根本装不下。
  代价是精灵必须带裁剪偏移。
- **`_sequence.json` 是打包器写的，字段名是 camelCase**，和工具箱其余协议的 PascalCase 不同，
  所以它有独立的 `AtlasJsonContext`。混淆会导致读不到字段，而且是**静默丢弃**。
- **旧素材按约定由工具箱直接删**（用户已确认）。第一次真跑会删掉 `Material/<动作>/` 下
  那批旧的逐帧贴图和精灵。

## 六、2026-09-17 晚：两处「刷新了却看不出变化」的根因

Sk2 同步成功之后，界面依旧报「二技能 删除 24 项 / 新增 23 项」。查下来是**两个独立的
bug 叠在一起**，各自的证据都留在 `runtime.log` 与磁盘产物里。

### 1. 刚检测出来的结果被会话缓存盖回去（UI 侧）

日志（同一次刷新，相隔不到一秒）：

```
[DEBUG-seqfacts] step=5 frames=294 withUnreal=154 withToolbox=271   ← 刚检测完
[Refresh Selection Result] restored=0
[DEBUG-seqfacts] step=5 frames=163 withUnreal=23  withToolbox=140   ← 又被盖成旧的那份
```

路径是：`DetectUnrealPublishChangesAsync` 建完树 →`SetLoadedPublishStep(5)`
→`ReturnToWorkflowStep(5)`；而后者会走 `RestoreWorkflowStepCache(5)`，老老实实从
`tool/UnrealSync/sync-<key>-step5.json` 读回上一次写下的差异，**当场覆盖**刚建好的树。
用户看到的就是「点了重新加载，列表一点没变」。

第二份数字小的原因是另一半：缓存里存的是一份「待办清单」，
`FilterCachedPublishChanges` 按设计把 `Unchanged` 剔掉了。序列树的**动作节点自己就是
`Unchanged`**，被剔掉之后「Unreal 现有 N 个帧位」无从得知，帧也全部配不成对。

修法：

- `RestoreWorkflowStepCache` 增加「这棵树已经属于这一步」的短路条件
  （`_hasImportDetection && _loadedPublishStep == step && 树非空 && 角色一致`）。
  第三步与第五步共用同一个树的槽位，只有 `_loadedPublishStep` 分得开；
  换角色时 `SelectSource → ResetImportOperation` 会把它清零，冷启动照常从缓存恢复。
- 第五步的 `FilterCachedPublishChanges` **不再剔 `Unchanged`**（第三步照旧）。

### 2. 帧的身份在图集时代被比错了（协议侧）

导出清单里，一帧的 `objectPath` / `assetName` 是**贴图**。图集改造之后，
一个动作的 23 帧全都指向同一张 `Misaka_Sk2`，而 C# 侧算出来的「规范贴图名」是
`Sk2_Frame00..22` —— 永远对不上，于是每一帧都被判成「要改名」，
`ExpandSequenceChange` 把它摊成 `:delete` + `:add`，正好 23 对。

真正能区分帧的是 **Flipbook 关键帧挂的精灵**：复用位置共用同一个精灵，
所以 23 个帧位只对应 17 个精灵，而精灵名是按「素材目录里第几张图」生成的
（`SequenceActionCatalog.GetFrameSpriteName`，和打图集、生成同步计划同一套规则）。

修法（三段都要，缺一段就还是错）：

1. 导出侧 `_ordered_flipbook_frame_assets` 把关键帧上的精灵带出来
   （`spriteName` / `spriteObjectPath`）。精灵本来就已经读到了，以前是读完丢掉。
2. 工具箱侧 `UnrealBridgeToolboxSnapshotService.AddSequenceFrames` 按同一套规则
   算出每一帧**应当**落在哪个精灵上（枚举素材目录 → 文件序号 → 精灵名）。
3. `IsCanonicalSequenceFramePair` 在两侧都带精灵名时按精灵名比。
   **但只在 Unreal 已经换成图集布局的动作上生效**（动作载荷 `layout` 以 `atlas:` 开头）：
   还停在逐帧旧布局的动作，精灵名是历史导入留下的（按帧序号命名），
   拿它比工具箱按素材序号算出来的名字，会把本来没问题的帧判成要重做
   —— 这一条我在实机冒烟里踩到过，第一次跑反而把 Click 从「无差异」变成「4 删 4 增」。

### 3. 顺带修掉的重复计数

`ExpandSequenceLayoutRebuilds` 会给「需要重建」动作下的每一帧补一条 `:add`。
内容也变了的那一帧前面已经被摊成 `:delete`+`:add`，于是又补一层，出现 `:add:add` ——
同一张图被数两遍。现在跳过已经带 `:add`/`:delete` 后缀的条目。
